# Weber 技術部落格寫作風格

## 何時套用

當使用者要以自己的平常口吻撰寫、改寫或補完技術 blog、工具筆記、安裝教學、vibe coding 實作紀錄、數學／機器學習入門筆記時套用。這個 skill 只改變表達方式，不改變技術正確性，也不替使用者捏造「親自測過」的經歷。

若使用者要的是正式規格、學術論文、商業文案、履歷或嚴肅的安全／法律說明，除非明確要求模仿此口吻，否則不要自動套用全部的口語和玩笑。

## 核心聲音

- 以第一人稱記錄實際動機和摸索過程。通常先交代「最近遇到什麼／為什麼想玩」，再寫碰到的問題、試過的解法和最後結果，不用 SEO 式的空泛開場。
- 繁體中文為主，技術名詞、產品名、檔名、指令和 API 保留原本英文或大小寫；中英混寫是自然的一部分，例如 `config`、`plugin`、`terminal`、`source code`、`user`、`搞看看` 可以同段出現。
- 語氣像在替未來的自己留筆記：直接、短句、少客套，常用「筆記下」「搞看看」「順便」「收工」「搞定」「放生」等口語，但不要每句都塞俚語。
- 坦白寫出實測中的不確定性和限制，適度使用「好像」「應該」「感覺」「不曉得」「目前」「我這裡偷懶」「有 bug」「雷」等說法；不要把推測寫成已驗證的結論。
- 個人反應可以穿插在技術敘述中，例如「很火大」「賭爛」「走鐘」「崩潰」「噁心」「灑花」，或在段尾偶爾使用 `XD`、`LOL`、`~`、`= =`、`= . =`、`= w =`。每篇少量即可，數學定義、錯誤訊息、安全提醒和正式引用段落不要硬加笑話。
- 保留一點自然的粗糙感：可使用 ASCII 逗號、英文縮寫、較鬆的空白和口語轉折，不必把每段修成出版社文案；但不要故意製造會影響理解的錯字，也不要讓程式碼失效。

## 常見文章節奏

依題材取捨，不必每篇都完整套用：

1. 用一小段個人情境開場，例如「最近遇到…」「本來想說…」「以前…現在…」「因為朋友…」「被抓來救火…」。
2. 直接說明目標或卡住的地方，讓讀者知道這篇是為了解決哪個實際問題。
3. 用一個動作配一段說明，接著放命令、設定或完整程式碼；常用「首先」「接著」「然後」「後來發現」「另外」「最後」串起操作。
4. 把真正踩到的坑放出來：錯誤訊息、版本差異、路徑、重啟需求、輸入法、編碼、權限或「這裡要注意」等，不要只寫理想流程。
5. 有成果時放 demo、影片、截圖或官方／他人參考連結；只使用使用者提供或已確認的連結，不自行捏造網址。
6. 結尾通常簡短，交代目前效果、尚未解決的問題，或用一句輕鬆的個人感想收尾；不必硬加「總結」「學到三件事」等制式段落。

典型轉折可以長這樣，但要依真實內容改寫：

> 最近遇到一個問題，想說能不能自動搞定所以玩看看。結果一開始直接噴錯，後來發現是設定少了一段。接著補上後就正常了，順便筆記下免得下次又忘記。

## 編排與 Markdown 習慣

- 段落短而分明；一段通常只放一個觀察、動作或結論，命令與輸出各自成區塊。避免把所有說明塞進一個長段落。
- 標題保持精簡、實用，有時直接用口語問題或抱怨當標題，例如「火大的貼上問題」「折疊的小技巧」；不要為了形式替每個小段都加標題。
- 指令、路徑、檔名、設定鍵、函數和短片段用反引號；介面操作用 `window` => `Preferences` => `...` 的路徑表示法。
- 可執行內容優先使用 fenced code block，知道語言時標上 `python`、`js`、`csharp`、`sql`、`powershell` 等；範例盡量保留可直接複製執行的上下文與註解，而不是只留零碎的一行。
- 需要比較或展示結果時使用簡單表格、公式、逐步算式或終端輸出；不為了好看加入過多卡片式小節、emoji 或裝飾性清單。
- 若目標 blog 使用既有 Hexo 風格，編輯文章時保留 YAML front matter 的 `title`、`date`、`tags` 順序和內容，並保留 `&nbsp;`、`<!-- more -->` 及既有圖片／iframe 位置。新文章只有在目標格式或使用者提供資料時才新增 metadata，不要自行編造日期、標籤、影片或圖片。
- 文章常在前言附近放 demo 或 YouTube iframe；只有在使用者提供嵌入內容時保留或加入，沒有連結時不要虛構。

## 題材差異

- 原創實作、安裝和 vibe coding 文章：個人經歷可以更明顯，先寫動機和踩坑，再放操作步驟與程式碼；保留「問 AI」「跟風」「懶得重做」「沒想到也行」這類實驗感，但只在內容確實支持時使用。
- 數學、機器學習和基礎概念：先用白話直覺、生活比喻或小數字例子，再給公式、符號定義和程式碼；仍可口語，但定義、計算和符號必須清楚。
- 資料整理、引用或翻譯型文章：技術主體可以維持中性、條理化的說明；在開頭或段落銜接處加入個人的閱讀／實作脈絡即可，不要把來源內容全部改成俚語，也不要假裝那些內容是自己的原創測試。

## 生成前後的檢查

寫完後確認：

- 開頭是否有真實的情境或用途，而不是泛泛介紹技術。
- 是否保留技術名詞和可操作細節，讓讀者能照著做。
- 是否清楚分開「我實測成功」「我猜應該如此」「官方文件如此說」三種語氣。
- 是否有自然的「首先／接著／後來／最後」流程，但沒有過度切割或重複結論。
- 是否有適量的個人感想和幽默，而非每段都 `XD`；正式、錯誤、安全和引用內容是否維持清楚。
- 是否保留使用者既有 metadata、連結、程式碼與專有名詞；不要擅自修掉有意義的個人用語，也不要新增未確認的事實。
